# AMPAS — Lean 證明驗證管線，以及它做不到什麼

**English: [README.md](README.md)**

這個專案把送審的 Lean 4 證明，拿去跟**事先凍結的參考陳述**比對。整套設計只為了講清楚一件事：

> Lean 核心接受一條定理，意思是這份證明在**它實際用到的公理與定義之下**通過型別檢查。
> 不代表原本那句自然語言的數學主張被證明了。

這兩件事之間有一段距離，這裡大部分的工程都花在那段距離上，以及避免把任何單一檢查器的結論講得比實際更強。**哪些東西檢查不到，寫得跟檢查得到的一樣詳細**——要採信這裡的任何結果，請先讀 [ASSUMPTIONS.md](ASSUMPTIONS.md)。

## 實際上做了哪些檢查

一份送審證明是一個 `.lean` 檔，聲稱證出了某條凍結的參考陳述。它要通過這些關卡：

| 關卡 | 這一關能證明什麼 |
| --- | --- |
| **沙箱編譯** | 以非特權帳號執行，受信任的 olean 掛成唯讀，限制 CPU、記憶體與輸出檔大小，編譯前後都對受信任檔案做雜湊比對 |
| **核心重放**（`leanchecker`） | 用 Lean 自己的核心，從 olean 把每一個宣告重新檢查一遍 |
| **第二套核心**（[lean4lean](https://github.com/digama0/lean4lean)） | 第二套核心重檢同一批 olean，**兩套都通過**才可能認證。上游自己的說法是「直接從 C++ kernel 實作衍生而來……並不真的是獨立實作」，所以這買到的是**近親之間的一致**，不是獨立確認——見 ASSUMPTIONS A2 |
| **第三道檢查**（[`harness/kernel3`](docs/review-third-check.md)） | 用 Python 從零寫的型別檢查器，和 Lean 不共用任何程式碼。只對**項層**提供旁證 |
| **公理稽核** | 把遞移用到的公理拿去對每條主張各自的政策；另外標記 `sorryAx`、原生求值、陳述裡出現的 `opaque`、`unsafe`、`partial` |
| **依賴閉包檢查** | 陳述依賴到的每一個常數，**連定義本體一起**，跟參考環境逐一比對 |
| **陳述比對器** | 把 elaborate 後的陳述跟凍結版本比對；可要求結構完全相同，或放寬到核心的定義等價 |
| **反例搜尋** | 一條陳述在被凍結之前，先用有界搜尋嘗試推翻它，結果簽進紀錄裡。Fermat 的主張在 n = 5 死在這一關 |
| **形式化簽核** | 內容定址的凍結、由機器推導型別的 guard 定理、Ed25519 簽章，加上漂移偵測 |

最後一關**沒辦法自動化**，這個專案也不裝作可以。詳見 [docs/review-formalization.md](docs/review-formalization.md)。

### 外部驗證題組

語料是寫這套管線的人自己寫的，所以另外找了數學史上的真實案例來測——那些題目的答案在這個倉庫存在之前很久就由別人定下來了。四段史實、八條主張、十六份送審。

- **Fermat**（約 1640 年）斷言每個 Fermat 數 $F_n = 2^{2^n}+1$ 都是質數，他手算驗到 $F_4$。這個主張是**錯的**。
- **Euler**（1732 年）推翻了它：$F_5 = 4294967297 = 641 \times 6700417$。

| 送審內容 | 預期 | 結果 | 被哪一關攔下 |
| --- | --- | --- | --- |
| Euler 的反駁，用因數分解證出來 | 認證通過 | **認證通過** | —（只用到 `propext` 一條公理） |
| Fermat 的主張：先驗他驗過的那幾項，剩下寫 `sorry` | 拒絕 | **拒絕** | 公理政策（`sorryAx`）＋ `SORRY` 標記 |
| Fermat 的主張，**完全沒有 `sorry`**，把缺口塞進一條 `axiom` | 拒絕 | **拒絕** | 公理政策，而且會指名那條公理 |
| Fermat 的主張，**每一行都真的證出來了**——但證的是 `n ≤ 3` 的限縮版，卻掛著一般主張的名字 | 拒絕 | **拒絕** | 陳述比對器 |
| Euler 的陳述，但證的是 $2^{32}$ 不是質數，不是 $2^{32}+1$ | 拒絕 | **拒絕** | 陳述比對器 |

第三列最值得停下來看：沒有 `sorry`、沒有多加公理、Lean 寫得完全誠實、兩套核心都接受——問題只在於這份形式化**根本不是它掛名的那條主張**。這種情況下，唯一擋在它和一張認證之間的，就只有陳述比對器。

後來又照同樣的形狀加了三段（`reference/claims_history.json`，11 份送審，全部與預期相符）：

| 史實 | 那條假主張 | 由誰定案推翻 |
| --- | --- | --- |
| Mersenne，1644 | $2^{67}-1$ 是質數（他清單上 $p=67$ 那一項） | Cole，1903：$2^{67}-1 = 193707721 \times 761838257287$ |
| Euler，1769 | 沒有五次方數是四個正五次方數之和 | Lander 與 Parkin，1966：$27^5+84^5+110^5+133^5 = 144^5$ |
| Euler 之後，1772 | $n^2+n+41$ 對每個 $n$ 都是質數 | $40^2+40+41 = 1681 = 41^2$ |

挑這三段是要打在不同的層上，而它們測出來的東西比「11 份全部對了」更有價值：

- Euler 的多項式在有界搜尋下死在 $n = 40$；Mersenne 那一項**也**死在有界搜尋下——判定程序用試除在幾分鐘內找出因數 193707721，所以搜尋自己重現了 Cole 1903 年的結果。
- Euler 的 sum-of-powers 猜想是**假的，而搜尋碰不到它**：1966 年那個見證需要五個變數都到 144。它對一條假主張回報「沒有反例」。那就是有界數值搜尋的本質，而且是在一條不是這個倉庫挑的主張上示範出來的。
- 而這組語料在管線裡抓到**四個缺陷**，而且全是同一類錯誤——衍生標籤不是從它旁邊的資料算出來的，或者根本沒有資料支撐。層歸因表用檔名前綴認定攻擊，所以**包含 Fermat 那四個在內，所有外部攻擊從 Fermat 題組加進來那天起就一直不在表裡**；一個 control 欄位我寫成 `target_claim_is` 而不是 `target_claim_is_true`，對人讀起來是對的，對程式是不存在的；第三道檢查的狀態寫著「已裁定」而旁邊的裁定欄位是空的，而它指的那些裁定本身也還沒有人確認；同一個狀態還被算成抓到了四個它其實什麼都沒抓到的攻擊。第五個發現：`evidence/ablation.json` 無法被 `verify.sh` 重現——它有一列只有 tier 3 會產生。全部記在 ROADMAP 6a。

一條史實主張固定下來的是**答案**，不是形式化。每條 Lean 陳述是否真的在說那句歷史句子所說的事，仍然是人的判斷，而且還沒有人做過：新目錄裡每一個 review 區塊都是 `PENDING`。

## 自己動手驗證

分四個層級。每一層都能單獨成立：跑不到的層級，不會影響已經跑完的層級的結論。

```bash
git clone https://github.com/lcat2000/ampas-lean.git && cd ampas-lean

# 第 0 層 — 不需要 Lean，幾秒鐘跑完
pip install pytest
python3 -m pytest tests/test_third_check.py -q -k "not pipeline"

# 第 0–1 層 — 只需要固定版本的 Lean 工具鏈，約 6 分鐘
pip install -r requirements.txt
./scripts/bootstrap.sh
./scripts/verify.sh 1

# 第 2 層 — 加上第二套核心
./scripts/build-lean4lean.sh && ./scripts/verify.sh 2

# 第 3 層 — 加上 Mathlib 的主張（約 20 分鐘，要從原始碼編譯 Mathlib）
./scripts/build-mathlib-tier.sh && ./scripts/verify.sh
```

完整步驟在 [INSTALL.md](INSTALL.md)，包含稽核器連結失敗時怎麼繞過。

**建議先跑第 0 層。** 它完全不需要 Lean，而它測的正是第三道檢查的**適用範圍**：拿手寫的偽造匯出檔去餵它，看它會不會拒絕——statement 模式的匯出必須被擋掉、兩個能證出 `False` 的偽造 inductive 規格不准被背書、而小消去那組對照必須照樣被拒。這些測試存在的理由，就是不讓日後任何改動悄悄放寬「結果乾淨」的意思。

## 這個專案不能證明的事

以下是簡版，完整清單和每一項的證據在 [ASSUMPTIONS.md](ASSUMPTIONS.md)。

- **形式化忠不忠實，機器判不出來。** 凍結、簽章和 guard 能做到的是：讓人的判斷變成可稽核、可歸責、而且不會無聲走鐘。它們沒辦法讓那個判斷變正確。
- **反例搜尋不是真的證據。** 它能做的是：不讓一條「明確為假」的陳述被凍結——這件事有價值，Fermat 的主張就是死在這裡。但「找不到反例」的意思是**在一個已登錄的小值範圍內**找不到；把範圍設成 Fermat 自己手上的證據（n ≤ 4），它就什麼都找不到。而且它對「陳述是否符合原文語意」完全沒有發言權。13 條裡有 4 條它根本碰不到，因為 `PL.Derives` 和 `EL.Derives` 沒有判定程序；那幾條的紀錄會寫 NOT_SEARCHABLE 並附上原因，而不是安靜地放行。完整的誤讀清單在 ASSUMPTIONS A1b。
- **多套核心一致，證據力沒有看起來那麼高——而且比原本寫的更低。** 2026 年陸續出現幾個 Lean 核心的健全性 bug，其中一個案例裡，拿另一套獨立核心去交叉檢查，結果**那套核心也接受了**那份非法證明——因為它自己有另一個無關的 bug（[Tao, 2026-10-09](https://terrytao.wordpress.com/2026/10/09/what-mathematicians-should-know-about-the-lean-theorem-proverquestions-of-reliability-and-ai/)）。**實作各自獨立，不等於失效各自獨立。** 更正（2026-10-14）：這個倉庫原本把 lean4lean 說成「另一位作者獨立寫的核心」，那是錯的。上游自己的 README 寫著它「直接從 C++ kernel 實作衍生而來……並不真的是獨立實作」。所以這裡跑的交叉檢查，**獨立性這個前提從一開始就不成立**。見 ASSUMPTIONS A2 與 ROADMAP 1.3。
- **第三道檢查只能旁證項層，僅此而已。** 它不會去推導一個 inductive 規格合不合法，而 `tests/forgeries/` 裡那兩個偽造，就是從這個缺口證出 `False` 的。它的來源查核會把這類宣告**明白列出來**，而不是替它們背書。
- **受信任的基礎縮小了，但沒有消失。** Lean 的 **elaborator**（也就是產生 olean 的那一步）、作業系統、沙箱，全都還在信任範圍內。
- **Mathlib 只涵蓋一條主張**，依賴錐 387 個 olean，不是整個程式庫。
- **簽章現在綁定到一把由審查者保管的金鑰——而「保管」是一個聲明，不是它的證據。** 13 份簽核全部由 `kai-chang-2026-10` 簽署，那把金鑰是在擁有者自己的機器上生成的，從未出現在建置這個專案的容器裡；公開的金鑰紀錄寫明了這件事，因為「誰保管私鑰」沒辦法從金鑰本身看出來。它能證明的是：這些紀錄由持有該私鑰的人簽署，且凍結之後沒有被改過。它**不能**證明持有者就是紀錄上寫的那個人——沒有憑證、沒有信任網、也沒有簽章過的 commit 鏈把這把金鑰綁到任何 GitHub 帳號，所以那行 custody 是被描述的當事人自己的宣稱。要獨立查核，得透過別的管道從他手上取得金鑰指紋。
- **多數忠實度判斷仍未經獨立審查。** 13 條全部由**寫這套管線的同一個助理**審的（見 [REVIEW-CHECKLIST.md](REVIEW-CHECKLIST.md)）。**13 條全部**已由擁有者本人逐條讀過並確認。那是一次獨立於管線作者的閱讀——而「獨立」正是先前缺的那個性質。它改動了這個專案，不是替它背書：EL-IND 的 text 把等式理論的「平凡化」誤寫成「不一致」（錯的——純等式理論恆有單元素模型）；PL-AXIOM-IND 的 guard 效力被高估（它只排除「完全證不出東西」的演算）；兩條假主張對照組把主張與對它的真假判斷混在同一個欄位，使 `faithful` 語意含糊，現已拆成兩個欄位；「第五個 Fermat 數」對 F₅ 而言易生誤解；還有一處效能說法是無證據的斷言。全部已更正。

  **仍然缺的：** 審查者是依貼出的定義判定，沒有自己重跑 Lean——所以忠實度判斷和核心結果出自不同的人，這正是重點，但也意味著沒有任何一方同時查核了兩邊；金鑰的保管狀態由持有者自己宣稱，沒有綁到任何外部身分；而且一個讀者不等於公開審查。
- **`unreviewed/` 不是交付內容**，也沒有任何程式會載入它。說明見該目錄的 README。

## 目錄結構

```
reference/     凍結的陳述、guard、主張目錄、簽核紀錄、來源基準、版本固定、裁定紀錄
corpus/        測試資料：正確的送審證明、13 個攻擊、Fermat 題組
harness/       驅動程式、Lean 稽核器、第三道檢查、基準與歸因工具
tests/         51 項測試，含不需要 Lean 的範圍測試與偽造向量
scripts/       bootstrap 與分層驗證腳本
evidence/      這份紀錄的執行結果，附每個檔案的用途索引
mathlib-tier/  選用的 Mathlib Lake 專案。刻意獨立，核心主張才不會誤取 Mathlib 依賴
docs/          兩份審查文件與建置註記
unreviewed/    隔離起來的程式碼，留著供比對，沒有任何東西載入它
```

## 接下來要做的事

[ROADMAP.md](ROADMAP.md) 依優先順序排列，前幾項是：

1. **別再把「兩套核心都通過」當成最強的證據。** 它已被證實擊得破（Tao, 2026-10-09），而且更糟：**這套管線的第二套核心從來就不是獨立實作**——上游自己說它「直接從 C++ kernel 實作衍生而來」（ROADMAP 1.3a，2026-10-14 更正）。[con-leche](https://github.com/leanprover/con-leche)（它的「接受」被**證明**蘊含集合論模型存在）在這裡 43 秒接受一份真實送審，已作為選用層提供（`scripts/check-with-conleche.sh`，[評估](docs/CONLECHE-EVALUATION.md)）。但它**也接受 `A06_wrong_statement`**——所以 verified kernel 同樣補不了忠實性那個缺口。
2. **第三道檢查的三個 inductive 假設性質，現在各有一道獨立且做過差分測試的 pass**：正性（3285 個歸納型）、遞子形狀與 iota 規則（各 3410 個遞子），全部 0 個違反。但剩下的假設是**移位**而不是消失：這三道查的都是「宣告是否符合 Lean 會遵守的規則」，沒有一道能證明**那份匯出真的來自 Lean**——所以擋下偽造的仍然是來源查核。見 ROADMAP 2。
3. **把簽章用的金鑰綁到這個專案之外的身分。** 2026-10-13 起，13 份簽核都由擁有者保管的金鑰簽署，而不是由建置容器保管——那個缺口已經補上。剩下的是：除了紀錄自己這麼說之外，沒有任何東西把那把金鑰和他本人連起來。把指紋發佈在別的地方，或改用簽章過的 commit，才能讓一個陌生人自己查核這件歸屬。
4. **把審查擴到一個讀者以外。** 一份確認已經獨立於管線的作者（這正是原本缺的那個性質），但它不是公開審查。
